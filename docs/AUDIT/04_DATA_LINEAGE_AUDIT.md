# Milestone Audit: Data Lineage & Real-Time Traffic Ingestion

**Project:** Bengaluru Smart Traffic Coordination System  
**Audit Scope:** Provenance, transformation, storage, and presentation of every metric; external real-world traffic telemetry investigation; data classification  
**Auditor:** Senior ITS Engineer & Geospatial Data Architect  
**Date:** October 30, 2026  
**Status:** COMPLETE (Read-Only Audit)

---

## 1. Executive Summary

This audit examined every data source, pipeline, formula, and display element across the repository to determine whether the project ingests, processes, or displays actual real-world traffic data from Bengaluru.

**Core Finding:** The project currently possesses **ZERO live external traffic data ingestion**. There are no integrations with TomTom, Google Maps, HERE, MapmyIndia, Bengaluru Traffic Police (BTP) live feeds, CCTV cameras, induction loops, or physical traffic signal controllers.

Every live traffic metric displayed on the dashboard (vehicle counts, queues, wait times, speeds, and emissions) is **100% synthetically generated** by the local Eclipse SUMO microscopic simulation stepping in the background.

Furthermore, several labels in the frontend UI are misleading, presenting simulated simulation steps as "Real-time observation".

## 3. Strict Classification of All Data Sources

In accordance with strict ITS engineering standards, every data item utilized by the system is classified into one of six categories:

1. `LIVE OBSERVATION`: Real-time telemetry from physical sensors, cameras, or external traffic provider APIs.
2. `HISTORICAL OBSERVATION`: Empirical data recorded from historical events (e.g. government crash reports).
3. `SIMULATED DATA`: Synthetically computed state generated by the SUMO microscopic simulation engine.
4. `HARDCODED DEMO DATA`: Static constants or mock values embedded directly in code or fallback configs.
5. `PREDICTION`: Estimated future traffic states computed by mathematical algorithms or ML models.
6. `RECOMMENDATION`: Suggested signal timing adjustments or advisory notices.

### Classification Table:

| Metric / Data Element | Originating Source | Classification | True Nature |
|---|---|---|---|
| **Active Vehicle Count** | `traci.vehicle.getIDCount()` | `SIMULATED DATA` | Vehicles simulated in current SUMO step |
| **Junction Queue Length** | `traci.vehicle.getSpeed() <= 0.1` | `SIMULATED DATA` | SUMO vehicles halted on approach lanes |
| **Corridor Average Speed** | SUMO lane mean speeds | `SIMULATED DATA` | Microscopic simulated speed |

| **Physical Bengaluru Traffic**| N/A | **NONE** | No connection to actual physical city infrastructure |

## 4. Complete End-to-End Metric Lineage

The following table traces every displayed metric from its raw origin to the UI component:

```
[Raw Origin] ──> [Processing File] ──> [Storage] ──> [API Endpoint] ──> [Frontend Component]
```

### Detailed Trace:

1. **Active Vehicles & Throughput**
   - **Original Source:** Eclipse SUMO microscopic simulation runtime (`traci.vehicle`).
   - **Processing File:** `traffic_service/corridor_metrics.py::record_step()`.
   - **Transformation Logic:** Counts active IDs via `traci.vehicle.getIDCount()`; increments throughput counter when a vehicle departs exit edge `40696223#1`.
   - **Storage:** In-memory `_cached_metrics` in `simulation_service.py`; persisted every 5s to `traffic_metrics` table in SQLite.
   - **Backend Route:** `GET /api/traffic/metrics` and WebSocket `/ws/traffic`.
   - **Frontend Ingestion:** `App.jsx` (`metrics` state) $\rightarrow$ `OverviewKPIs.jsx`.

2. **Junction Approach Queues**
   - **Original Source:** Eclipse SUMO lane state queries (`traci.lane.getLastStepVehicleIDs`).
   - **Processing File:** `traffic_service/state_extractor.py::get_lane_queue()`.
   - **Transformation Logic:** Filters vehicle IDs on approaches whose speed $\le 0.1\text{ m/s}$.
   - **Storage:** `_latest_states` in-memory dictionary.
   - **Backend Route:** `GET /api/traffic/live` and WebSocket `/ws/traffic`.
   - **Frontend Ingestion:** `LiveCorridorView.jsx` and `SignalStatusPanel.jsx`.

3. **Carbon & Fuel Emissions**
   - **Original Source:** SUMO HBEFA vehicle emissions API (`traci.lane.getCO2Emission`, `getFuelConsumption`).
   - **Processing File:** `traffic_service/state_extractor.py::extract_emissions()`.
   - **Transformation Logic:** Accumulates milligrams per second over `step_length` to yield mass in mg. CO2 is divided by $1,000,000$ to produce kg. Fuel was previously divided by $1,000$ (converting mg to grams, mislabelled as litres); corrected volume divides mass by fuel density ($750,000\text{ mg/L}$ or $750\text{ g/L}$) to report estimated gasoline-equivalent volume. Fuel mass in kg remains canonical.
   - **Storage:** In-memory `_cached_metrics`; persisted to `traffic_metrics` SQLite table.
   - **Backend Route:** `GET /api/traffic/metrics` and WebSocket `/ws/traffic`.
   - **Frontend Ingestion:** `EmissionAnalytics.jsx` and `OverviewKPIs.jsx`.

4. **Accident Risk Zones**
   - **Original Source:** BTP South Division 2020–2023 road safety audit reports.
   - **Processing File:** `scripts/run_accident_pipeline.py` $\rightarrow$ `traffic_service/risk_mapper.py`.
   - **Transformation Logic:** Formulas: $\text{Severity} = (5 \times \text{Fatal}) + (2 \times \text{Non-Fatal})$; $\text{CRI} = \text{Severity} \times (1 + \text{CorridorBonus} + \text{JunctionBonus})$.
   - **Storage:** `outputs/risk/risk_zones.json` $\rightarrow$ seeded into `risk_zones` SQLite table during `init_db()`.
   - **Backend Route:** `GET /api/risks`.
   - **Frontend Ingestion:** `RiskHotspotsPanel.jsx`.

5. **Benchmark Comparison Data**
   - **Original Source (Backend):** `outputs/corridor/corridor_multi_seed_summary.csv` generated by `scripts/evaluate_corridor.py`.
   - **Original Source (Frontend Chart):** Hardcoded static JavaScript array in `frontend/src/components/ControllerComparison.jsx`.
   - **Transformation Logic:** Backend parses CSV into `ExperimentCompareResponse`. Frontend ignores the response for its chart and renders static constants.
   - **Storage:** Static CSV on disk.
   - **Backend Route:** `GET /api/experiments/compare`.
   - **Frontend Ingestion:** `ControllerComparison.jsx` (renders table from API, but chart from hardcoded array).

## 6. Recommendations for Real-World Data Ingestion

To transform this system into a true hybrid digital twin capable of assimilating real Bengaluru traffic, the following architecture must be added:
1. **Live Traffic Ingestion Service:** An asynchronous background worker polling TomTom Traffic API (Flow Segment Data & Incident Details) or Google Maps Routes API for Silk Board (Hosur Road, ORR, Madiwala).
2. **SUMO Dynamic Insertion (DFROUTER / TraCI Route Injection):** Converting real-world travel speeds and congestion delays into SUMO vehicle insertion rates (`traci.route.add`, `traci.vehicle.add`).
3. **Clear Dual-Stream UI:** A side-by-side indicator distinguishing between **Real-World Live Observation** (TomTom/Sensor feed) and **Simulation Digital Twin** (SUMO microscopic model).
